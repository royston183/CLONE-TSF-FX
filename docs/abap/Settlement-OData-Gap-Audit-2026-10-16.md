## Existing APIs with missing or incorrect application wiring

These findings should not all become requests to create new OData services.

1. **Accounting Completed does not enforce the original FX-document checks.** The live button calls `markAccountingComplete` (`bo-post-accounting-settlement/index.tsx:279`), which reads only the deal and local positions (`accounting.ts:44`). It never loads the FX legs, Doc 1, DSS mapping or no-invoice model flag. Its FX branch expects `ZT_TYPE = 'FX'` in TRD_POS, although current MO writes trade invoice rows there, and BO `positions.ts` explicitly excludes old synthetic FX rows. Original `POST_F01:57` onward checks mapped FX Doc 1 for no-invoice models; for invoice models it checks FI-required invoice documents and the mapped/DSS FX Doc 1 before status 22. The program-shaped `accountingRefusal` in `logic.ts:160` exists, but the live handler does not call it.

   A dependency-only reproduction returned `ok: true` and captured a request for status 22 with just one posted trade row and **no FX-document evidence**. With no trade rows it refused completion, even though no-invoice models need their FX checks instead. [Reproduction](settlement-audit/reproduce-accounting.mjs) / [captured results](settlement-audit/accounting-reproduction.json). These were mocks, with no SAP or database writes. Fix the live handler and preferably enforce the same checks in a backend completion action.

2. **Amend End Date remains a placeholder although the deal update path exists.** MO `index.tsx:350` validates the input then shows `ACTION_WAITING.amend`. Original `INV_F01:494` updates both `DEALID-ZREV_DEDATE` and every matching `TRD_POS-ZP_DATE`, then commits. `fxUpdate('tsfDealId', ...)` already exists for header writes. Wire the operation and ensure its trade-position update reaches SAP; the missing header write alone does not prove a new OData service is necessary.

3. **BO transaction Update is still gated.** `index.tsx:317` returns `ACTION_WAITING.txnUpdate`. Original `POST_TXN_P:131` updates the TSF bank fields through the FX or option change BAPI. MO already writes the corresponding AppStr fields. Reuse an appropriate verified transaction update contract and implement the option branch.

4. **FX invoice-model override is read but not applied to settlement configuration.** Original `POST_PBO:423` and the equivalent MO PBO override the resolved model with `DEALID-ZFX_INV_MODEL`, with additional subtype/model-resolution rules. MO `api.ts:588` selects SET_FX/SET_TYP from MC `ZMOD_ID`; BO `api.ts:259` uses `header.fxModelId`, which prefers MC model. Both display `ZFX_INV_MODEL` without using it for these configuration reads. This can choose the wrong sequences, FI flags and mappings even when every table read succeeds. Implement original model resolution before requesting configuration.

5. **Heads Up is incorrectly described as a missing reminder API.** Current MO opens an empty list and `api.ts:312` refers to EMLBD / READ_TEXT. Actual screen 9004 calls `INV_DIFF:64` -> `PROCESS_DATA:92`, using RULE_BT, INV_REF, BIL_ADJ and SET_TYP plus the transaction legs to calculate invoice/deal differences and FX/ITM/OTM actions. These table resources are already used elsewhere in the app. Implement this calculation/view; option inputs remain a separate gap. EMLBD belongs to the separate email class in `INV_TOP`, not this screen's data load.

6. **P&L uses a simplified formula.** MO `logic.ts:124` computes `(second rate - first rate) * first amount` only for D2. Original `INV_F01:586` processes roll/cancel groups and cash amounts; at `788` and `1017` it calls `BAPI_EXCHANGERATE_GETDETAIL` for rate type M on the value date. A middleware TCURR lookup already exists in `shared/fx/exchange-rate.ts`, but the P&L path does not use it. Port the original calculation and rate semantics; account for missing roll/option inputs and SAP quotation factors rather than assuming a new rates service is absent.

7. **View Trade Invoice and document hotspots are incomplete.** MO displays `VIEW_INVOICE_WAITING`; BO shows a summary of currently loaded legs. Original `INV_F01:138` and `POST_F01:52` submit `ZSGTSF_RDEAL_ID_INV`. Provide the actual report/viewer route or an equivalent report API, separately from reading settlement rows. The submitted report's full implementation is outside these two exports.

8. **Execution completion omits an original email side effect.** The exported MO `INV_F01:214` onward updates status 21 and invokes `lcl_limit_email_sender->send_email`. `INV_TOP:1349` reads EMLBD configuration for category `02`, code `E024`. App `settlement.ts:404` only writes the status. If this 2026 addition is required, implement a backend notification action tied to successful completion. Its runtime inputs also need confirmation: the exported caller declares local amount/year/date variables without an evident assignment in that handler. No email was sent during this audit.

## Printing requires separate treatment

**Initiate Printing** and **Print Letters/PDF** are separate original operations. Current MO `index.tsx:347` and `418` return waiting messages.

- Original `INV_F01:379` **Initiate Printing** rebuilds/persists TRD_POS rows; its body does not itself invoke an Adobe form. Its immediate gap is this action and SAP position persistence, even though the app's waiting text lists PDF functions.
- Actual form generation is in `INV_POST:2585` onward (`READ_TEXT`, `FP_FUNCTION_MODULE_NAME`, `FP_JOB_OPEN`, `FP_JOB_CLOSE`) and `INV_BS:121` onward. It also uses original bank/address and amount-to-words data. A backend rendering operation returning the generated PDF would cover the form behavior.

## Already integrated; not blanket missing-OData findings

- FX posting uses `trmflowpost/TreasuryFlow/...PostFlows` in `posting.ts:100` / `154`; invoice FI posting deep-inserts `fiaccdoc/JournalEntry` with `_Item` at `posting.ts:385`. Current `.env.local` sets `VITE_BO_LIVE_POSTING=true`. Current availability was blocked by 401, but the integration code is present. The 9 October [blocker note](BO-SETTLEMENT-POSTING-BLOCKER.md) describes older application behavior and must not be treated as the current implementation inventory.
- Deal/header/status, model rules, SET_TYP, SET_FX, invoice adjustments/references, companies, bank partners, invoice difference/IN_SPOT writes and TCURR already have middleware paths. Middleware REST coverage counts as an existing backend path even where it is not OData.
- MO settlement already writes TSF bank fields and `ZtsfExeCo` through `trmfxapp/TrmFxApp`, including DSS mirroring, and statuses 20/21 through middleware. The relevant TSF fields appear in the previously saved [APP_STR DDIC](vtbfha-audit/ZSGTSFTR_APP_STR.ddic.asddl). Do not classify this entire TSF payload as another missing-field set. **Unverified equivalence:** the original writes VTBFHA through `ZSGTRMFM_VTBFHA_EXPORT` plus the change BAPI; the frontend instead updates APP_STR. No backend implementation proving propagation to the real transaction was available in this audit, and live access was unauthorized. Confirm that synchronization before calling the legacy and new paths equivalent.
- SAP DMS file actions and house-bank account reads have clients; the specific DMS link/configuration and payment-instruction gaps above remain.

## Validation and suggested order

Focused existing MO/BO tests were executed. All loaded test cases passed, but BO `logic.test.ts` **fails to load** because it imports `NOT_SETTLED`, which `logic.ts` does not export. That pre-existing test/API mismatch and tests that still model synthetic FX positions do not verify the live completion flow. No application or test source was modified.

Suggested implementation order: fix live accounting completion and model resolution; replace local SAP business-state/configuration substitutes; implement clearing/payment-instruction and option coverage; correct document matching/readback; then complete amendments, Heads Up, P&L, report links, printing and any required notification behavior. Resolve the HTTP 401 and repeat metadata/read-only checks before assessing publication or exercising posting.
